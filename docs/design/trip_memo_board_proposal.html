DESIGN PROPOSAL

여행 메모 — 상세 위쪽에 쌓아두는 한 줄들

여행을 준비하다 보면 일정도 숙소도 준비물도 아닌 것들이 남는다. 환전 얼마, 유심 어디서, 저장해둔 블로그 링크 같은 것들. 지금은 그걸 둘 자리가 없어서 준비물에 억지로 끼워 넣거나 카톡으로 흘려보낸다. 상태 카드와 tab 줄 사이에 한 줄씩 쌓아두는 자리를 만든다. 적는 칸과 링크 칸은 나눠서, 무엇이 열리는 주소인지 앱이 짐작하지 않게 한다.

1

지금은 둘 자리가 없다

여행 폼의 메모는 여행 하나에 한 덩어리뿐이라 항목을 더할 수 없다. 준비물에 적으면 챙길 것 목록이 링크와 메모로 지저분해진다.

2

글과 링크는 다른 것이다

한 칸에 섞어 적게 하면 앱이 주소를 짐작해야 하고, 짐작이 틀리면 사용자는 왜 안 열리는지 알 수 없다. 칸을 나누면 무엇이 링크인지 사용자가 정한다.

3

입력은 sheet에서

상세 맨 위는 이미 뱃지·제목·기간·상태로 빽빽하다. 여행 spec도 입력은 모두 bottom sheet로 연다고 정해두었다. 카드에는 담긴 것과 메모 담기 한 줄만 남긴다.

구현 방향

추천안(메모 카드)을 기준으로 적는다. 확정되면 docs/spec/trips.md와 docs/test_plan.md를 먼저 고치고 코드에 들어간다.

자리와 모양

  • 상태 카드(_TripDetailHeader) 아래, 고정 tab 줄(AlagagiPinnedScrollHeader) 위. 스크롤과 함께 올라가는 영역이라 tab 줄을 밀어내지 않는다.
  • 메모가 없으면 안내 한 줄과 입력칸만 남긴다. 카드 자체를 숨기지는 않는다. 숨기면 이 자리가 있다는 걸 알 길이 없다.
  • 한 줄은 내용 + (있으면) 링크 열기. 카드 모양은 기존 두 가지(AlagagiCardGeometry) 안에서 compact를 쓴다.
  • 카드 안에 폼을 펼쳐두지 않는다. 메모 담기 한 줄을 누르면 sheet가 올라온다. 여행 spec의 입력은 모두 bottom sheet로 연다를 그대로 따르고, 고치기도 같은 sheet를 연다.
  • 긴 메모는 두 줄에서 접고 기존 펼쳐 읽기(AlagagiFullTextCue)로 전문을 연다.

링크

  • sheet는 내용과 링크 (선택) 두 칸으로 나눈다. 한 칸에 섞어 적게 하고 앱이 주소를 짐작하면, 짐작이 틀렸을 때 왜 안 열리는지 알 길이 없다.
  • 링크 칸은 scheme을 안 적어도 된다. 기존 lib/src/shared/openable_link.dart의 normalizedOpenableLink를 그대로 써서 blog.naver.com/...도 열린다.
  • 열 수 없는 값을 적었으면 저장할 때 sheet에서 알려준다. 담고 나서 조용히 pill만 빠지면 사용자는 오타를 눈치채지 못한다. 저장은 막지 않고 안내만 남기는 쪽을 권한다.
  • pill에는 host만 보여준다(blog.naver.com). 390px에서 전체 주소는 무조건 잘린다.
  • 여는 통로는 여행 화면이 이미 받고 있는 onOpenExternalLink를 쓴다. 새로 뚫지 않는다.

데이터와 Firestore write

  • 새 collection을 만들지 않는다. tripItems에 kind: 'memo'를 더해 기존 문서·규칙·재시도 채널을 그대로 쓴다. 메모는 타임라인에 나오지 않고 종류 picker에도 없다.
  • 내용은 title, 링크 칸은 link에 그대로 들어간다. 두 field 모두 이미 있고 길이 상한(80자 / 500자)도 이미 규칙에 있다.
  • Firestore write는 명시적인 동작에서만 난다. 담기 / 고친 내용 저장 / 지우기가 각각 tripItems/{itemId} 한 문서를 쓴다.
  • 입력칸 타이핑, 스크롤, tab 전환, 링크 열기는 Firestore write를 만들지 않는다.
  • 저장 결과와 실패 후 다시 시도는 여행이 이미 쓰는 저장 상태 채널(tripSaveStatus)이 맡는다. 새 배너를 만들지 않는다.
  • 지우기는 여행의 다른 항목과 같이 확인 sheet를 거친다. 둘 중 누가 담았든 둘 다 지울 수 있다.

규칙 변경

  • firestore.rules의 kind in ['stay','transport','packing','plan']에 'memo'를 더하고 docs/firebase_setup.md를 함께 갱신한다.
  • tools/firestore_rules_test에 메모 담기·고치기·지우기를 실제 쓰기로 통과시키는 case를 추가한다. 규칙은 요청당 표현식 1000개 한도가 있어, 조건을 늘릴 때 실제로 돌려보지 않으면 다시 막힌다.

테스트

  • domain: 메모를 담으면 tripItems 한 문서만 쓰고 타이핑은 쓰지 않는다. 메모는 타임라인·숙소·준비물 목록에 끼지 않는다.
  • widget: 링크 칸에 적은 메모에 열기 pill이 뜨고 누르면 정규화된 주소로 밖을 연다. 링크 칸이 비면 pill이 없다.
  • widget: 내용만 적고 담아도 저장된다. 링크는 선택이다.
  • widget: 지우기가 확인 sheet를 거치고, 취소하면 그대로 남는다.
  • rules: 위 규칙 test.

정해주셔야 하는 것 하나

여행 폼에 이미 메모 칸이 하나 있다(trip.note, 500자, 상세에서 카드로 보임). 새 메모 목록이 생기면 메모가 두 군데가 된다.
· A안(권장) — 여행 폼의 메모 칸을 없애고, 기존에 적어둔 값은 상세 메모 카드 맨 위에 회색 한 줄로 계속 보여준다. 새로 적는 것은 전부 목록으로 간다. 데이터를 지우거나 옮기지 않는다.
· B안 — 둘 다 그대로 둔다. 여행 폼 메모는 ‘여행 한 줄 소개’, 새 목록은 ‘적어둘 것’으로 성격을 나눈다. 다만 사용자가 둘을 구분해야 한다.
